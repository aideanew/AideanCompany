# 三、本体系执行步骤的缺陷（基于真实架构，逐条带证据）

## D1【致命】执行层不存在：CLI 调用是"散文"，不是代码

- **证据**：全仓无任何拉起 CLI 干活的实现；只有 `restart_console_v3.py:105-112` 的 `--version` 探活、`console.py:255` 一行注释。
- **根因**：`cli-delegation.md` 是**规范文档**，其"执行者"是"读到它的那个 LLM"。系统把"执行机制"外包给了模型的自觉与记性。
- **后果**：`异常.md` 里"0 次 CLI 派工、0 个子 agent"不是事故，是**必然**。换任何模型、任何提示词都只是概率问题。
- **修法**：执行必须由确定性代码（Runner/Dispatcher）承担，见 §4。

## D2【致命】派工包结构性缺失 `delegate_to`，三段提示词互相矛盾

- **证据**：`console.py:694-712 dispatch_via_manager()` 生成的包只有「编号/目标/工作目录/要求与约束/完成标准/报告要求」——**没有 CLI、没有模型、没有 `delegate_to`、没有证据路径、没有六节要求**；而 `cli-delegation.md §2` 明令"任务包 `delegate_to` 原样填写"。更糟的是它发给 Manager 的 prompt 是 `用 a2a_call 工具向 {target} 发送下面内容（全文原样发送）`——**明确要求 Manager 原样转发，禁止扩写**，于是 Manager 侧 `manager-SOUL.md §4` 的"补 `delegate_to`"规制被代码层指令压掉。
- 同时：`configs/worker-SOUL-template.md` 与 `console.py:335-389 soul_template()` 生成的 worker SOUL **通篇没有 claude/codex/opencode 字样**。
- **后果**：走控制台这条**唯一被允许的派工路径**，worker 永远收不到"用哪个 CLI、用哪个模型、要落什么 transcript"。
- **修法**：包格式加字段并机器校验非空（见 §5 改动点①）。

## D3【严重】"证据三件套"里有一件是可伪造的弱门

- **证据**：`console.py:741` `audit("manager", f"{kind}_reply", ...)` 的 `ok` 是 **`hermes -z` 进程退出码**，与 worker 是否干活无关；任何一次派工都会写这条记录。
- **含义**：`异常.md` 提出的 T12 第 1 条"audit.log 有该任务 `dispatch_reply`"**证明不了执行**——它只证明控制台自己调起过一个 hermes 进程。
- 真正硬的只有第 3 条（`<task>-cli.log` + 最高权限启动行），但**代码里没有任何地方生成或校验它**：`machine_verify()`（`652-684`）只看 `verify_cmd` 退出码。
- **修法**：把 `dispatch_reply` 降级为辅助信号；新增不可伪造门（见 §5 改动点③）。

## D4【严重】状态机可被"一键人工收口"绕过全部门禁

- **证据**：`POST /tasks/<id>/close`（`1834-1845`）直接 `transition(task,"DONE","console",note)`，**不校验 `verify_ok`、不校验 reviewer 判定、不校验 transcript**；`validate_task_integrity` 的 R2 还给 manager/supervisor 人工收官开了豁免口子。
- **证据链闭合**：`tasks.json.bak-fake-done-20260915` 存在；`fleet/reports/aideanbot_v3_completion_report_20260915.json` 里 9 个角色全填「圆满完成无返工」、`platform` 全写 `Console`、模型写成 `DeepSeek V4 Flash-3.0-flash`（名册里不存在的串），并宣称 "All tasks passed machine-door verification" —— **而同一时刻 T-030~T-038 在 tasks.json 里是 DRAFT**。
- **修法**：`/close` 加前置门并去掉豁免；见 §5 改动点②。

## D5【严重】终态门（acceptance）被写成"文档存在性"检查，且路径错位

- **证据**：`P-004/project.json` 的 `acceptance[].verify_cmd` 形如
  `grep:fleet/projects/AideanBot/BE-01/task-package-BE-01.md:订阅执行引擎端到端闭环`。
  而 `machine_verify()`（`659-672`）以 `Path(cwd)/rel` 解析，`cwd = E:/Code/AideanBot` → 实际去找 `E:\Code\AideanBot\fleet\...`，**实测 `Test-Path = False`** → 必然 `[FILE MISSING] FAIL`。
- 更关键：即便路径修对，该门只查"**任务包文档里出现过这个词**"，而任务包本身就能满足它 → **终态"全绿"可以在零代码交付下达成**。
- 同时 `tasks.json` 里同样的 T-026~T-029 的 `verify_cmd` 却是**真命令**（`pytest backend/tests/test_be01_subscription_run.py -q`、`npx vitest run tests/fe02-spaces-subs.test.tsx`）→ **两套门并存且不一致**，"绿"的语义不可复现。
- **修法**：终态门只认真实命令退出码，且 AC 必须指向**产物**而非**计划文档**；显式带 `cwd`。

## D6【架构级】"限额自动切模型"在当前设计里物理不可达

- **证据**：worker 模型烧在各自 profile 的 `config.yaml`（`roster.json` → `write_role_config()` `417-427`）；换模型 = 改配置 + **重启网关**，而 `model-pool.json:14` 自己写着 `hermes_profile_swap: 需用户授权或预批重启槽`。代码里换模型逻辑为 0，`launch:model_switch`（`model-pool.json:115-119`）只是一条"指望 LLM 记得发"的审计事件。
- **对照**：本机 `hermes kanban create --model/--provider` 与 `hermes kanban set-model <id> <model> [--provider]`（**下次派工生效**）正是核心.md 要的"限额自动切模型"，**Hermes 原生已有，自研层却做不到**。
- **修法**：模型切换改为 task 级 override，禁止热改 profile。

## D7【严重】重试策略三套口径互斥，且 429 覆盖不到真正出错的那一层

- **证据**：`model-pool.json:16-22` = **10s×10**；`fleet-baseline.json:10` = `backoff_429_seconds: [60,120]`；`console.py:719-727` 硬编码 **60s→120s 两次**；`cold-start.prompt.md:35` + `executor.template.md:185` 又写 **10s×10**。
- 且 `console.py` 的退避只包住"Manager 那一句 `hermes -z`"，**worker/CLI 侧真实发生的 429 完全不被覆盖**。
- **后果**：核心2(1) "10 秒重试 10 次 → 换模型"在实现上不存在。
- **修法**：`model-pool.json.retry` 作为唯一真相源，删除控制台硬编码。

## D8【严重】"实时同步 / 实时进度"没有生产者和持久载体

- 进度字段只在**接收端**存在（`launch_event()` `114-137` 只落审计，不产出）；`/api/stream` 只是回放 `audit.log`，**没有心跳生成器**；`dispatch_via_manager` 的线程是 `daemon=True`（`742`）→ **控制台一重启，所有在跑任务全丢**；而 launcher 本身是 IDE 里的一个 LLM 会话，**关窗口即断**。
- **对照**：Kanban 有 SQLite 板 + dispatcher daemon + heartbeat + claim TTL + crash 回收 + stranded 检测。
- **后果**：核心1(2)(3)"实时同步 / 实时告诉进度 / 断点继续"三个诉求都缺载体。

## D9 可观测性只有 HTML 页，没有机器可读 API，也没有鉴权

- 写路径 `/tasks/<id>/{plan,dispatch,verify,review,rework,close}` 全是 **form 编码 + 返回 HTML**；没有 `/api/tasks`、没有任务 JSON 快照；`_redact()` 只防 Key 泄漏，**不防身份伪造**——本机任何进程都能写 `actor=manager`。审计"不可篡改"只是名义（append-only 文件，谁都能追加）。
- **后果**：让 LLM 用 `curl` + 解析 HTML 是脆弱环节；完成度表的"平台/模型"无从交叉核对。

## D10 前置条件重、无自愈

- `dispatch` 前要求 worker 端口在听（`1766`）、`review` 前要求 reviewer 端口在听（`1804`）；角色启动是同步 `hermes -p <rid> gateway run`（`573`），失败无重试/无巡检。
- **当前实测**：8 worker 网关全 offline + `a2a 工具已启用 = false`（`fleet_health()` `1462-1463`）→ **今天连派工都发不出去**。（该检查的字符串匹配 `"enabled  a2a"` 也偏脆弱，可能是误报——但两种情形都是缺陷。）
- **对照**：`hermes pause/resume` 急停、kanban `diagnostics`（stranded）、crash 回收。

## D11 四份"真相源"互相打架，导致完成度表注定填不准

- 名册口径分散在：`AGENTS.md`、`默认基础配置.md`、`state\roster.json`、`model-pool.json.role_model_map_default`、各 profile `config.yaml`。
- **实测冲突举例**：`roster.json` worker-a = `sensenova/sensenova-6.8-flash-lite`，而 `model-pool.json:110` worker-a = `nvidia/nemotron-3-ultra`；roster 里 be-2/be-3/worker-b = `b.ai/qwen3.8-flash`，而 `model_pool_state.json` 显示 `bai: unreachable(http_401)`。
- **后果**：核心2(2) 的完成度表"平台/模型"不是态度问题，是**结构性不可能填对**。

## D12 "不试错启动"没落实，且与官方实测口径冲突

- 冷启动只给一个 `restart_console_v3.py`；CLI 启动行散落三处（`cli-delegation.md §2`、`executor.template.md §1`、`cold-start.prompt.md 硬约束`），且与官方口径冲突：
  - `claude --dangerously-skip-permissions` 在**交互模式**默认选中 "No, exit" → 无人值守必须走 `-p`；

# 三、Hermes 用法学习成果（能直接落地的部分）

## 3.1 拉起第三方 CLI 的三种正规姿势

| 姿势 | 用法 | 适用 |
|---|---|---|
| `terminal(background=true, notify_on_complete=true)` | 返回 `session_id`，Hermes 追踪生命周期/输出，完成时通知 | **本舰队的正确答案**。长任务必须带 `notify_on_complete`，否则"silent bg"永远等不到结果 |
| `terminal(pty=true)` | 真实 PTY | Codex/Claude Code 这类交互式 CLI 的会话模式；Hermes 文档明确点名"PTY mode: Set pty=true for interactive CLI tools (Codex, Claude Code)" |
| `hermes chat -q "..."` 一次性 | 无 PTY 的 fire-and-forget | 单任务；`console.py` 现在派 Manager 用的就是这个（`hermes --yolo -z`） |
| tmux | `tmux new-session -d -s backend -x 120 -y 40 'hermes'` + `send-keys` | 多 agent 并行；raw PTY 对 `prompt_toolkit` 有 `\r`/`\n` 问题，官方要求走 tmux |

关键区别（官方对比表）：

```
delegate_task      → 同进程、工具集是父级子集、几分钟、不能交互
spawn hermes 进程  → 独立进程、全工具集、可 PTY、可跑几天
```

**"子 agent"这个词在本体系里被三种东西占用了：Hermes 的 `delegate_task`、spawn 出的 hermes 进程、以及 claude/codex/opencode 进程。`cli-delegation.md §6` 试图定义"子 agent = CLI 进程"，但 `delegation` 工具集在 worker 上被裁剪、在 Manager 上没被裁剪——口径是碎的。**

## 3.2 MCP 配置（Hermes 侧）

`~/.hermes/config.yaml` 的 `mcp_servers`。worker-a 现在有 3 个：

```yaml
mcp_servers:
  chrome-devtools:     {command: npx, args: [-y, chrome-devtools-mcp]}
  sequential-thinking: {command: npx, args: [-y, '@modelcontextprotocol/server-sequential-thinking']}
  exa:                 {command: npx, args: [-y, exa-mcp-server, --tools=web_search_exa,...], env: {EXA_API_KEY: ${EXA_API_KEY}}}
```

四个必须记住的坑：

1. **stdio MCP 子进程不继承 shell 环境变量**，只继承安全基线变量。API Key 必须显式写 `env:`。worker-a 的 `exa` 用了 `${EXA_API_KEY}` —— 如果 worker 的 `.env` 里没有这个变量，exa 工具静默失效（无 Key，无报错，模型只是"没这个工具"）。
2. **工具名是 `mcp__<server>__<tool>`**（文档口径），旧 skill 文档写 `mcp_<server>_<tool>`。做机器门匹配时两个都得认。
3. `trust: untrusted` 会让所有非 `readOnlyHint` 的写工具强制走审批面 —— 在无人值守网关上等于死锁。本舰队所有 MCP 都是 `trust: full`（默认），即**完全信任**，风险点。
4. `tools.include/exclude` 支持 fnmatch glob。给 worker 收敛工具面应该用它，而不是靠 LLM 自觉。

**Hermes 能反向被第三方工具当 MCP 用**：`hermes mcp serve` 写进 Claude Code 的 `claude_desktop_config.json`；`hermes proxy` 起一个 OpenAI 兼容代理，让 Codex CLI / Cline / Aider 直接指向它。这意味着**"在第三方工具下配置 MCP"有两条方向**，本舰队目前一条都没用。

## 3.3 Skills 配置（这是本舰队最严重的一个洞）

Hermes：`$HERMES_HOME/skills/*/SKILL.md`，兼容 agentskills.io。worker profile 下确实有 skills（`profiles/be-2/skills/autonomous-ai-agents/claude-code/SKILL.md` 等）。

tools_config.py:592-598  # agent.disabled_toolsets "runs LAST so it overrides everything"

**这九个 worker 全部无法加载任何 skill。** 每个 profile 目录里躺着 `autonomous-ai-agents`、`claude-code`、`codex`、`opencode`、`native-mcp` 这些官方 skill——worker 一个都读不到。`d6.md` 里"skills 是文件夹 + SKILL.md，各基座都认""员工 prompt 只写一句话引用 skill，模型会自动加载"——**这句话对当前舰队是假的**。

## 3.4 无头模式启动行（回答核心3.1"感觉每次都要试错"）

## 3.5 A2A：Hermes 上游的一个真实 bug（影响本舰队）

上游 issue **#78050** 与本舰队架构直接冲突：

- `a2a` 是 `kind: platform` 的插件，**deferred by design**。CLI/TUI 进程永不 import 它 → `a2a_call` 等五个工具**根本不注册**。`hermes tools enable a2a` 的 opt-in UI 在 CLI 里不可达（toolset 不在静态 `TOOLSETS` 注册表里，`resolve_toolset('a2a')` 返回 `[]`）。只有 gateway/web_server 进程启动时才注册。
- 即使注册了，还有第二道闸：`a2a` 在 `_DEFAULT_OFF_TOOLSETS` 里，`_get_platform_tools` 会把它从 inbound 会话剥掉。
- `hermes tools enable a2a --platform a2a` → **`Unknown platform 'a2a'`**（`tools_config.py:5399` 校验静态 `PLATFORMS` 注册表，`a2a` 不在其中）。
- 绕过方案的最小配置 `platform_toolsets.a2a: [a2a]` 会把 inbound 会话压缩到约 2 个 toolset——**terminal/file/web/browser 全部掉出**。

**对照本舰队实测**：worker profile 里都没有 `platform_toolsets.a2a`。这解释了为什么 `/api/health` 的 `"a2a 工具已启用"` 字符串匹配返回 false，也解释了为什么 Manager 的 agent-card 上挂着 `toolset.a2a`（Agent Card 的 `advertised_toolsets` 是另一套口径）却没人真能用。**"Manager 有没有派工工具"这个问题，答案是：取决于哪个进程、哪个 platform、哪道闸，而舰队没有任何一处文档说清楚。**

# 四、缺陷分析：核心.md 的四个诉求，逐条对照实际架构

## 缺陷 A —— 核心3.1「没有教如何启动 Hermes 和 CLI，每次都试错」

**这是五个缺陷里根子最深的一个。** `restart_console_v3.py:105-115` 把最高权限启动行写成 `print()`：

```python
clis = [("claude", ["claude","--version"], "claude --dangerously-skip-permissions"), ...]
for name, ver_cmd, launch_line in clis:
    r = subprocess.run(ver_cmd, ...)      # 只跑 --version
    print(f"                启动行: {launch_line}")   # 只打印，从不执行
```

一份"探活脚本"成了"启动行"的唯一程序载体。**"打印一行字符串"和"执行一行字符串"之间差着一个执行器，而这个执行器在整套系统里不存在。**

四处口径冲突：

| 来源 | claude 启动行 |
|---|---|
| `cli-delegation.md §2`（自称权威） | `--permission-mode acceptEdits` |
| `executor.template.md` | `--dangerously-skip-permissions`（并声明上面那条降级为回退行） |
| `cold-start.prompt.md` | `--dangerously-skip-permissions` |
| `project.json.cli_overrides.max_permission_launch` | `--dangerously-skip-permissions` |
| `project.json.cli_overrides.flags.claude` | `--permission-mode acceptEdits`（同一文件内部自相矛盾） |

而且按 2026-09 最新官方口径，这四处的 claude 行**全都过时了**（缺 `--bare`、缺 `--max-turns`、缺 `--output-format json`）。

**修复方向**：启动行必须变成一个**单一机器可读源**（如 `cli-launch.json`，字段化 `binary/flags/cwd/env/transcript_path`），`cli-delegation.md` 降级为只读说明文档，所有引用点 grep 这一个文件。且这个文件必须是**可被 `python -c` 直接执行**的——不是给人读的字符串。

## 缺陷 B —— 核心2(1)「429 → 10s × 10 次 → 切模型」

现状：`agent.api_max_retries: 3`（worker-a config）。**3 次，不是 10 次，间隔也不是 10s。** 且 `fallback_providers` 只有 worker-a/b/c 有，Manager/pm-1/fe-2/be-2/be-3/reviewer-1 五个 profile 该段为空。

叠加另一个矛盾：`core.md` 要"重试 10 次"，`cli-delegation.md §5` 要"CLI 重试 1 次 + 429 等 60s→120s 退避 2 次"，控制台派工线程是"60s→120s 共 2 次"。**三套重试策略，没有一套和 core.md 一致。**

更根本的问题：**429 重试应该发生在哪一层？**
- 模型层（Hermes `fallback_providers`）：只管 hermes 自己的 LLM 调用
- CLI 层（claude/codex/opencode 进程内）：无人可控
- 编排层（console.py）：能管，但目前 0 代码

**"worker 的 CLI 报了 429"这件事，当前架构里没有任何一层能看到**——因为 CLI 从未被拉起过，也因为没有 transcript 通道。

## 缺陷 C —— 核心2(2)「终局输出角色/平台/模型/任务/评分表」

现状：`console.py:1490` 硬编码 `"Manager","Hermes","agnes-3.0-flash"`，而真机 Manager 跑的是 `gpt-6-astra`。**这张表的"模型"列是写死的假数据。**

且"模型"这个字段**当前没有任何采集机制**：
- hermes 侧的 usage 落在 `state.db`，舰队不读
- CLI 侧的 `--output-format json` 会返回 `total_cost_usd` + per-model breakdown——**这是唯一能拿到真实模型消耗的通道，而舰队不用 json 格式**（`cli-delegation.md` 用的是 `--output-format text`）
- 95 个 A2A 回复里没有任何一个自带"我用了什么模型"

**结论：这张表在当前架构下无法真出。要出，必须改两处——CLI 调用改 `--output-format json`/`--json`，以及把该字段结构化采集进 launch-event。**

## 缺陷 D —— 核心3.2「测试环境禁用 GPT6，管理员用 agnes-3.0-flash」

**当前直接违规。** `profiles/manager/config.yaml:2` 是 `model.default: gpt-6-astra`，而 `model-pool.json:88-98` 自己标着 `env_scope: ["prod"]`、"测试环境硬禁"。`model-pool.json` 里有这个规则，**但没有任何代码读它做拦截**。它是给人看的。

## 缺陷 E —— 核心4「端口/hermes 被占用时问用户 Y/N」

现状有三个互不兼容的启动入口（`start-fleet.ps1` 的 12 个 `Start-Process`、`restart_console_v3.py` 的幂等自检、`POST /fleet/start` 网页按钮），**没有一个实现了"占用则询问"**。`restart_console_v3.py` 的口径是"无旧进程则不杀，幂等"——即**静默复用**，不问。`/fleet/start` 的行为未定义询问路径。

且 `/api/health` 要 30.8 秒（`console.py:1517` 同步调 `hermes --version` 最长 30s + `:1523` 同步调 `hermes tools list` 最长 60s + 19 次 socket 探测）。**任何默认超时的自动化轮询都会超时 → 判定"控制台挂了" → 放弃派工 → 退化成 curl 探测。这是缺陷放大器，也是 09-15 那次退化的直接推手。**

# 五、根因（一句话）

**这套系统把"机械动作"交给了 LLM 判断。**

`cli-delegation.md §6` 说"每个任务 1 次 CLI 调用 = 1 个子 agent"。但实际路径是：

```
console.py 拼 pack（无 delegate_to 字段）
  → hermes --yolo -z "用 a2a_call 发给 worker-a ..."     ← LLM 判断①：要不要调 a2a_call
    → A2A JSONRPC → worker 网关                            ← 4 跳，无鉴权
      → worker LLM 读中文指令                              ← LLM 判断②：要不要 shell out 到 claude
        → （应该在此起 CLI 进程）                          ← 无代码、无校验、无证据
```

`d7.md` 的 **ADR-005 已经写明**："确定性恢复由 Policy Engine 执行，Manager 不处理机械重试"。**这条 ADR 被写下来但从未实现。** 95 次 A2A 派工、114 次 `a2a_call`、319 个会话文件、0 次 CLI——就是这条 ADR 没落地的完整后果。

`delegate_to` 这个字段在整套系统里**没有结构化承载**：任务 schema（`console.py:1804-1807`）没有它，派工 pack（`:732-737`）没有它，唯一通道是 `task.detail` 自由文本里手写一句"CLI 委托: claude"。一个**文档约定 + 提示词口头要求**支撑着整个"多 CLI 协作"的核心卖点。

附带：worker 白名单只有 `E:\Code\AideanBot`，而 `cli-delegation.md` 在 `AideanCompany\fleet\configs\`、任务包在 `fleet\projects\`——**worker 按白名单规则读不到自己该照做的命令表。**

# 六、修复方案

## P0 —— 把 CLI 执行权从 LLM 手里收回来（解决缺陷 A/B/C）

**核心改动：在 `console.py` 新增确定性 CLI 执行器，`delegate_to` 变成结构化字段。**

新增 `POST /tasks/<id>/cli-run`（或在 `dispatch_via_manager` 后追加），由 console 进程直接 `subprocess.Popen` 拉起 CLI：

```
1. 从 tasks.json 读结构化 delegate_to: {cli, model, cwd, flags}
2. 从 cli-launch.json（单一真相源）取启动行，拼装
3. Popen 拉起，stdout/stderr tee 到 evidence/<task>-cli.log

## 二、头脑风暴：本体系执行步骤的缺陷分析

先一句话定性 `异常.md` 暴露的根因：**体系的“执行”只存在于提示词的叙述里，不存在于任何机器路径里**。19 次工具调用全是调度者（ZCode）用自己的 Read/Bash/curl 自查自证，`探测有效、执行无效`。据此，我把缺陷按执行链路六层拆开，并对照 `核心.md` 五个假设逐条找洞。

### 缺陷 A：启动层——没有“可执行的 runbook”，只有“可阅读的设想”

1. `核心.md` 问题 3 自己已经承认：“没有教如何启动 Hermes 和 CLI，每次都要试错”。但 d0–d12 全是架构与协议，**没有一份启动 SOP 规定：环境检查 → `hermes doctor` → 三个 CLI 的 `--version`/`auth list` → OPENCODE_SMOKE_OK 式冒烟 → 才允许派工**。试错的根源是“验收前移”缺失，不是文档不够多。
2. **环境事实未经验证就写进了设计**：d12 声称 Hermes 支持 Win11 原生，官方文档是仅 WSL2 [1][2][3]。设计文档里混入未核实断言，会让启动流程在第一步就翻车——这本身就是“试错成本”的来源之一。
3. 假设四（多 agents 开圆桌：claudecode 前端、codex 后端、opencode 产品）只给了角色，**没给会议协议**：谁主持、争议如何仲裁、会议产出物是什么格式、如何进入任务包。d9 的“三省六部+GSD 作大脑、Fleet 作执行”其实已经回答了，但假设四和 d9 之间没有接起来。
4. “都以最高权限启动（`claude --dangerously-skip-permissions`）"与 d0 自己列出的“治理层缺失（权限最小化/审批门/沙箱）”直接矛盾。三方工具都提供分级方案：Codex `profiles`（strict=read-only）[20]、OpenCode `permission` 字段 [21]、Claude Code 权限模式 [18]。**给每个角色按职责配沙箱档位，比全员最高权限更接近“全自动且可控”**。

### 缺陷 B：派工层——“必须调 CLI”只写在提示词里，没有长在代码路径里

1. `异常.md` 的补丁（T12 CLI 调用门 + 冷启动铁律）方向正确，但本质仍是**提示词约束 + 事后审计**：LLM 被要求“不许冒充执行”，可执行权仍在它手里。真正的修复是**让派工成为控制面的代码函数**——任务从 `READY` 到 `DOING` 的唯一通道是“拉起 CLI 子进程并登记 PID"，LLM 没有绕过它的工具。Hermes 的 `delegate_task`（自动 live transcript、结构化 status/usage/tool_trace）[9] 或 Kanban 认领 [10] 就是现成的代码级通道；自研舰队则应把 dispatch 做成 API 唯一写入口（`console_api_only` 已在补丁里，但要落到路由层实现，而非纪律）。
2. **“子 agent”一词三义**：ZCode 的 Agent 工具、Hermes 的 delegate_task、舰队的 Manager→worker 网关，在文档里混用。`异常.md` 只澄清了一次，但没有在 schema 层禁用歧义（例如任务包里 `worker_type` 字段必须枚举 CLI 名，不写"agent"）。
3. 缺少**并行写冲突预防**：d7 提出的 `write_set/read_set` 在调度前判 `A.write ∩ B.write`，这是对的；Hermes 的 worktree 隔离只解决隔离不解决冲突 [9]，两者要叠加，而当前执行步骤里没有这一环。

### 缺陷 C：模型池层——`核心.md` 假设五 + 核心 1/核心 2 的四个硬伤

1. **重试策略自相矛盾且有放大风险**：核心.md 规定"429 后 10 秒重试、共 10 次、再切模型”；d6 设计的是“指数退避 + fallback 链 + 兜底记录表”。固定 10s×10 次等于 100 秒内对限流端点打 10 连发，真实 429 窗口常常远大于此，只会换来封禁。建议统一为：指数退避（10s→20s→40s…）≤3 次 → 按优先级切下一个模型 → 全部失败进 Kanban 式**熔断锁定**（连续失败 N 次即停，等人工），而不是无限礼貌重试。
2. **优先级是静态的，没有健康探测和额度台账**：BAI 必须走 10808 代理、AMD“有限额度”、V3“较昂贵仅用于规划”——这些约束都写在注释里而不是配置里。模型池应每项带：`proxy_required`、`role_whitelist`（规划/编码/审查）、`budget_remaining`，派工前由探活程序（`probe_pool.py` 已有雏形）预检，而不是让 LLM“自己选合适的模型”。
3. **密钥管理是当前最大的安全事故隐患**：`核心.md` 把 7 家平台的 API Key 明文写在提示词文档里。这份文档每次都会被贴进调度上下文，等于密钥进入了每一个 CLI 的上下文、日志与 transcript。Hermes 生态的惯例是密钥只进 `~/.hermes/.env` 或 Bitwarden Secrets，配置里用 `${VAR}` 引用 [5][12]。**这批密钥应视为已泄露，建议立即轮换并从所有提示词文档中移除**（本回复不复制它们）。
4. **完成度表（角色|平台|模型|任务|评分）缺客观来源**：`异常.md` 第 5 条已经发现连平台/模型都对不上。评分若由 LLM 自评，就是又一个“自证”。正确做法：平台/模型从 transcript 自述 + 池探活**交叉程序校验**；评分由机器指标合成（gate 通过率、返工次数、token 消耗、耗时），LLM 最多给定性注释。表必须由 report 生成器从 events.jsonl 汇总输出，而非手填。

### 缺陷 D：验收层——事实层与语义层的权限没分开执行

d7 ADR-006 写了“Machine Gate 权威高于 Agent 自述、LLM 不能把 pytest 失败解释成 PASS"，但异常.md 显示 oracle 只查“字段在不在”。缺的三道门：① transcript ↔ 完成度表交叉一致性的**程序**（不是让人眼核对）；② `DONE` 状态只能由 verify 退出码 + launch-event 写入，提示词永远无权改状态（d7 的 `BLOCKED/FAILED` 区分也要落实，否则“环境坏了”会被记成“任务失败”）；③ 需求追踪矩阵（d3 已提出）——假设一“直到达成我所有需求”没有逐条需求的完成定义，`/goal` 式完成契约（目标+验收命令+范围+求助条件）[10] 是最低成本的补法。

### 缺陷 E：进度与同步层——探针和事件流混在一个管道里

`核心.md` 核心 1 要求“控制/展示界面实时同步、实时告诉用户进度”。异常.md 显示 `/api/launch-event` 里混着 `third_party_probe_DO_NOT_TRUST` 探针和业务事件，UI 若不加区分就会展示假进度。应规定：**进度展示只消费 `dispatch/worker_progress/model_switch/final_report` 四类事件**，探针事件打独立 tag 不进进度条；事件流 append-only（d7 已设计），UI 是它的唯一读者。

### 缺陷 F：调度权归属——Hermes 与自研舰队的定位还没做决策

d11 已经给出结论性判断：“Worker Runtime 这层可以先不自己造，真正值得自己造的是公司管理制度（TaskPack/Gate/Evidence/Lease/State）"[11]。当前执行步骤的缺陷是**没有把这句话变成 ADR**。两条路线都成立：
- **路线 1（快）**：Hermes 做编排层（delegate_task + worktree + live transcript + Kanban + doctor 冒烟），自研件收缩为 TaskPack schema + Machine Gate + Report 生成器；
- **路线 2（稳）**：自研舰队保留，但把 Hermes 当**第四个 Adapter**（d7 的 `PiAdapter` 模式），派工仍走控制面 API。
无论选哪条，异常.md 的 T12 三证据（dispatch_reply + transcript + launch-event）都应作为**不变的验收协议**写进 ADR-016。
