# 不正常，CLI 那段回答恰恰自证了“没走舰队流程”

一句话：它的回答是诚实的，但诚实的内容就是 `0 次 CLI 派工、0 个子 agent`。这在舰队 v3 里等于没干活，只做了 `curl` 手工探测。

## 1. 先对齐三个概念，你就知道问什么了

* `cc / claudecode / codex / opencode`：舰队干活的三种 CLI。`fleet/configs/cli-delegation.md` 和 `fleet/projects/P-004/project.json` 里定死了谁用什么：`worker-b/be-2` 走 `codex`，`worker-a/fe-2` 走 `opencode`，`claude` 走最高权限行 `claude --dangerously-skip-permissions`。真正的执行必须拉起这些 CLI 进程去跑任务包。
* `ZCode 的 Read/Bash/WebFetch/Agent`：第三方工具自己的内置工具。它列的 19 条全是这一类，和舰队 CLI 是两套东西。
* `子 agent`：舰队语境下不是 ZCode 的 `Agent` 工具，而是 `Manager(9900) -> worker 网关(9901-9911)` 这条链。启动器只许经 Manager 派工，worker 的 CLI 跑完必须回 `transcript + verify 退出码 + launch-event`。这三样都没有，就没有子 agent。

所以“是否调用了 cc”这个问题本身就是试金石：答“没调用过 cc，全是标准 ZCode 函数” = 承认没进舰队执行层。

## 4. 以后怎么防：把“必须调 CLI”写成机器门，不靠自觉

原因和假 DONE 同根：提示词没把它装进舰队，oracle 只查“字段在不在”、不查“怎么来的”。补两处：

新增 `T12 CLI 调用门`，每次验收必跑，缺一即 FAIL：

```powershell
# T12 CLI 调用门
# 1) audit.log 有该任务 dispatch_reply
# 2) launch-event 有 dispatch + done/final_report
# 3) evidence 有 <task>-cli.log 且含最高权限启动行
# 4) 完成度表该行 平台/模型 与 transcript 自述一致
# 任一不满足判未执行，不得 DONE
```
