# AideanAgentFleet 目录重构与核心实现修复计划

> 版本：2026-09-15-plan-v1
> 状态：仅建立计划，未执行验证，未启动 CLI，未派工，未迁移文件。
> 目标：以最小原子步骤解决 `初始设计/异常.md`，实现 `初始设计/核心.md`。

## 0. 总原则

1. 控制面必须由程序控制：状态、派工、验收、收口、重试、模型选择、权限、审计不得由自然语言决定。
2. 执行面可以使用自然语言：CLI/Agent 只负责在授权工作区内修改代码或文档。
3. 证据面只认机器证据：退出码、原始 transcript、文件差异、事件、审计和审批记录。
4. 单一写入口：任务状态只能经控制 API/任务存储服务修改，禁止直接编辑状态 JSON。
5. 任何 `DONE` 必须可反向追溯到任务、版本、执行者、CLI、模型、命令、证据、验收和审查。
6. 测试环境禁止 `gpt-6-astra`；密钥只允许进入受保护 secret store 或 `.env`，不得进入设计文档、日志、任务包和 transcript。
7. 本文件只描述后续执行顺序；本轮不执行验证、不启动服务、不调用外部 CLI。

## 2. 多层级执行路线

### L0：项目安全冻结

**目的**：防止修复过程中继续产生假完成。

原子步骤：

- S0.1 记录当前分支、文件清单和备份位置。
- S0.2 关闭自动派工和自动收口。
- S0.3 将当前所有 `DONE` 标记为“待完整性复核”，不凭报告恢复。
- S0.4 轮换 `初始设计/核心.md` 中已经出现过的所有密钥，并从文档、日志、报告、任务包中清除。
- S0.5 明确本阶段只读，直到用户批准进入实施阶段。

门禁：没有备份、没有密钥处理记录、没有冻结标记，不进入 L1。

### L1：统一术语与协议

建立四个机器协议：

- `TaskPack`：任务 ID、目标、输入、输出、允许目录、禁止操作、依赖、CLI、模型、命令、超时、重试、证据路径。
- `TaskState`：`DRAFT → READY → ASSIGNED → RUNNING → SUBMITTED → VERIFYING → REVIEWING → DONE/PARTIAL/REWORK/BLOCKED/FAILED`。
- `Event`：事件类型、任务、项目、角色、CLI、模型、PID、attempt、时间、来源、摘要、证据引用。
- `Evidence`：原始 transcript、启动命令、cwd、PID、退出码、git diff、测试输出、时间和哈希。

门禁：所有字段有 schema；自然语言报告不能代替字段；没有 TaskPack 不得派工。

### L2：启动与环境

小白操作顺序：

1. 打开 PowerShell。
2. 执行 `cd E:/Code/AideanCompany`。
3. 运行环境检查程序。
4. 检查 Hermes、三种 CLI、Node、Python、Git、WSL2/Windows 兼容性。
5. 执行 `hermes doctor`。
6. 对每个 CLI 执行版本、认证和非破坏性 smoke test。
7. 确认 `TEST_FLEET_ENV=1` 时 gpt-6-astra 被阻断。
8. 只有所有前置条件 PASS，才允许显示“可派工”。

门禁：任一 CLI、认证、工作目录、权限、代理、端口或 Key 检查失败，状态只能为 `BLOCKED`，不得继续。

### L3：确定性执行层

新增 Runner，负责：

1. 从 TaskPack 读取 CLI 与模型，不让 LLM 自选命令。
2. 校验二进制路径，避免 PATH 选错。
3. 使用非交互模式：Claude 使用 `-p`，Codex 使用 `exec`，OpenCode 使用 `run`。
4. 为每个任务生成独立 evidence 目录和 transcript 文件。
5. 记录 PID、命令、cwd、开始/结束时间、退出码、模型、CLI 版本。
6. 只允许白名单目录；并行任务使用独立 worktree 或不相交 write_set。
7. 任务超时、进程崩溃、窗口关闭后，保留状态并交给恢复器。

门禁：Runner 未成功创建启动记录和 transcript 索引，任务不得进入 `RUNNING`；没有原始 CLI 输出，不能进入 `SUBMITTED`。

### L4：持久化调度层

使用持久化队列（首选 SQLite/Kanban 适配层）：

- 原子 claim，防止两个 worker 抢同一任务。
- lease TTL，进程崩溃可回收。
- heartbeat，显示“正在运行”而不是人工猜测。
- DAG 依赖检查，前置未完成不得派工。
- write_set 冲突检查，不相交才允许并行。
- max_runtime、max_attempts、consecutive_failures 熔断。
- `pause/resume`，用户可急停但不丢状态。
- restart 后扫描 `RUNNING`，根据 lease 决定 resume/reclaim/block。

门禁：没有持久化 claim 和 lease，不允许宣称“支持断点继续”。

### L5：验收与收口层

机器验收顺序固定为：

1. CLI transcript 存在且时间晚于派工。
2. 启动命令与 TaskPack 的 CLI/model/cwd 一致。
3. 任务声明的产物存在。
4. `git diff/status` 与报告文件清单一致。
5. 真实测试命令执行并返回退出码 0。
6. 禁止把任务包文档关键词当终态验收。
7. reviewer 只能在机器门通过后审查。
8. 只有 reviewer `PASS` 或有独立审批记录的人工覆盖才可 `DONE`。
9. 人工覆盖必须使用独立状态 `MANUAL_OVERRIDE`，不能伪装为普通 `DONE`。
10. 完成度表由事件和证据自动生成，禁止 LLM 自评。

### L6：模型池与重试

- `model-pool.json` 是策略来源；Runner 是唯一执行者。
- 网络错误、429、5xx、超时按统一配置重试。
- 重试参数只允许一份：间隔、最大次数、抖动、熔断、候选顺序。
- 401/402/403/model_not_found 直接切候选。
- 模型切换必须是 task 级 override，不热改 profile。
- 每次切换写 `launch:model_switch`，记录 from/to/reason/attempts。
- 测试环境永远拒绝 gpt-6-astra。

### L7：可观测性与小白界面

页面只显示程序计算结果：

- 当前状态、前置任务、执行者、CLI、模型、PID。
- 最近事件、重试次数、剩余预算、预计时间。
- 证据是否齐全。
- 阻塞原因和下一步按钮。
- 探针事件与业务事件分频道。
- 用户能看到“等待用户”“等待网关”“等待模型”“正在执行”“等待审查”“已完成”。

自然语言只作为解释，不参与状态判定。

## 3. 逐条解决异常.md 的实施映射

| 异常 | 根治动作 | 完成标准 |
|---|---|---|
| 零 CLI 调用 | Runner 真实执行三种 CLI | 有真实 PID、命令、transcript、退出码 |
| `delegate_to` 缺失 | TaskPack schema 强制 `executor.cli`、`executor.model`、`command_template` | schema 校验失败即不可派工 |
| `dispatch_reply` 弱证据 | 降为辅助事件 | DONE 不依赖它，依赖 Runner evidence |
| `/close` 绕过门禁 | 关闭普通人工直收口，强制 machine gate + review gate | 非法请求返回结构化错误并写审计 |
| 文档 grep 假验收 | AC 指向真实产物和真实命令 | 每条 AC 有 cwd、命令、退出码 |
| 模型不会自动切换 | task 级 model override + fallback executor | 切换事件与实际命令一致 |
| 三套重试口径 | 删除重复配置，统一 policy reader | 运行时只读一个 retry policy |
| 重启丢任务 | SQLite queue + lease + heartbeat + reclaim | 杀进程后任务可恢复或明确 BLOCKED |
| 无鉴权 | API token、角色权限、来源校验、事件签名 | 未授权写请求被拒绝 |
| 网关离线无自愈 | doctor、watchdog、重启退避、熔断 | 失败原因可见，不能伪造在线 |
| 模型真相源冲突 | role/profile/pool 分层并定义优先级 | 运行时模型有唯一 resolved 值 |
| 启动命令试错 | command registry + 本机 help 校准 | 启动命令自动生成，不靠复制提示词 |
| 明文 Key | 轮换、扫描、secret store、提交钩子 | 设计文档和报告无明文 Key |

## 4. 五个核心假设的统一入口

### A：已有需求文档

输入：项目路径、需求文档、端口。

程序流程：`intake → document index → requirement matrix → TaskPack → plan approval → dispatch`。

### B：只有一句话需求

程序先创建 `INTAKE`，由产品/技术分析生成需求澄清表和候选计划。用户确认前，不创建可执行任务。

### C：检查遗漏并修复

先生成只读 `defects`，再按 P0/P1/P2 创建修复 TaskPack。测试任务不得修改产品代码。

### D：多人讨论

进入 `DISCUSS` 模式，角色只读；每轮有主持人、输入、输出、异议、决议和下一轮问题。最终必须生成 PRD 与决议记录，才可转 `PLAN`。

### E：自动选择模型

用户只提供候选范围。程序读取健康、角色能力、预算、代理、Key 状态和 fallback，生成 resolved model；模型由程序写进 TaskPack，不允许 worker 临场自行选择。

## 5. 小白操作手册（未来版本）

### 第一次使用

1. 安装并打开支持平台（原生 Windows 或 WSL2 只能选经过本机检查的一种）。
2. 打开控制台。
3. 点击“环境检查”。
4. 看到全部绿色后点击“新建项目”。
5. 输入项目名称、工作目录、需求文档路径、端口。
6. 点击“生成计划”。
7. 逐项查看任务包；确认无误后点击“批准计划”。
8. 点击“开始执行”。
9. 观察状态，不需要复制 CLI 命令。
10. 完成后打开“证据与报告”查看实际 CLI、模型、命令和退出码。

### 遇到失败

- 看到 `BLOCKED`：不要改 JSON；点击“查看阻塞原因”。
- 看到 `RETRYING`：等待程序重试，不重复点击派工。
- 看到 `MODEL_SWITCHING`：程序正在切换候选模型。
- 看到 `NEEDS_APPROVAL`：只执行页面要求的人工确认。
- 看到 `INTEGRITY_FAIL`：停止一切收口操作，导出报告交给管理员。
- 控制台关闭：重新打开控制台，点击“恢复任务”；不要重新创建同一任务。
